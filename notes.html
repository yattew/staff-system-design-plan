AI Case Study

Uber Michelangelo: The Pioneer of the Enterprise Feature Store

Week 23 • Production MLOps
First-Principles Architecture:

• Dual-Storage Architecture: Offline features computed in bulk via Spark into HDFS/Hive (optimized for high-throughput scans during training) paired with online low-latency features pushed into Cassandra/Redis (optimized for single-digit millisecond key-value lookups during live ride dispatch).
• Eliminating Training-Serving Skew: Centralized feature definitions in a shared registry. Features like "average driver ratings over 30 days" use the exact same transformation code in offline model backtesting as during online live inference.
• Point-in-Time Correctness: Time-travel joins guarantee that when generating training data for a ride in May, only feature values timestamped *before* that ride occurred are joined, preventing data leakage from the future.

✅ The Staff Architectural Lesson:

Feature calculation must be decoupled from both data ingestion and model training. A centralized Feature Store converts custom one-off data wrangling into shared, versioned, reusable enterprise assets.

⚠️ The Production Gotcha:

Synchronization lag. If the streaming pipeline updating the online Redis store experiences Kafka consumer lag, the model makes decisions on stale features. Health alerts on feature freshness SLAs are mandatory.

🎙️ The Staff Interview Soundbite:

"To prevent training-serving skew and silent model decay in high-frequency ML applications, I would architect a centralized Feature Store modeled after Uber Michelangelo. We compute features once via streaming engines into low-latency Redis for online inference, and mirror snapshots to our Data Lakehouse for point-in-time consistent training datasets."

AI Case Study

Netflix Nearline ML Architecture: Real-Time Personalization at Scale

Week 24 • Streaming ML
First-Principles Architecture:

• 3-Tier Decoupling: Offline (Spark batch matrix factorization overnight) → Nearline (Kafka + Apache Flink streaming pipeline updating session context in < 500ms) → Online (Low-latency recommendation ranking microservice).
• Event-Driven State Updates: When a user watches 30 seconds of an anime, Flink captures the playback event, increments genre affinities in an in-memory session cache, and re-ranks the candidate pool before the user navigates back to the homepage.
• Graceful Fallback & Circuit Breaking: If the nearline streaming pipeline suffers backpressure or downtime, the online layer seamlessly falls back to pre-computed static offline recommendations with zero user disruption.

✅ The Staff Architectural Lesson:

Don't try to run heavy deep neural networks end-to-end on every user click. Heavy models run offline to generate candidate sets; lightweight streaming scoring engines adjust rankings on the fly in real-time.

⚠️ The Production Gotcha:

Session state cache eviction. Inactive users must have their ephemeral session state evicted to prevent memory bloat, smoothly reloading baseline profiles on subsequent app launches.

🎙️ The Staff Interview Soundbite:

"For ultra-responsive personalization across hundreds of millions of users, I follow Netflix's 3-tier Nearline pattern: heavy matrix factorization and embeddings are trained offline, while an Apache Flink streaming pipeline consumes user interaction events to adjust ranking scores within 500ms, with immediate fallback to static offline candidates if streaming degrades."

Case Study

WhatsApp: 2 Million TCP Connections per Box (Erlang / FreeBSD)

Week 9 • High-Scale Chat
First-Principles Architecture:

• Erlang BEAM Actor Model: Rather than allocating a 1MB OS thread per user, Erlang creates lightweight user-space processes costing only ~2.5 KB of RAM each. 2 Million concurrent connections consumed only ~5 GB of user memory.
• FreeBSD Kernel Tuning: Tuned socket buffers to drop memory per socket down to bare minimums (kern.ipc.maxsockets bumped to millions; net.inet.tcp.recvspace and sendspace shrunk so idle connections didn't waste kernel memory).
• Ejabberd Stripping: Replaced bloated XML parsing with compact binary protocols and patched Mnesia database code to eliminate lock contention on shared routing tables.

✅ Why Erlang was the Staff choice:

Share-nothing actor model means one user's crash or timeout never impacts another. Built-in supervision trees automatically revive failed worker processes without restarting the server.

⚠️ The Production Gotcha (What to watch for):

Erlang message mailboxes are unbounded. If a fast producer sends messages to a slow consumer process, the mailbox grows indefinitely and silently exhausts RAM. Production Erlang requires explicit backpressure queue limits.

🎙️ The Staff Interview Soundbite:

"When designing a multi-million-connection chat gateway, thread-per-connection architectures fail due to OS thread context-switching and stack memory overhead. I would leverage the lightweight actor model (Erlang BEAM or Go goroutines with an epoll/kqueue event loop), paired with aggressive kernel socket buffer minimization, mirroring WhatsApp's 2M-connection architecture."

Case Study

Grammarly: Native Common Lisp Core Engine for AST Tree Parsing

Week 26 • High-Speed Parsing
First-Principles Architecture:

• Homoiconicity (Code-as-Data): In Common Lisp, data structures and code share the exact same representation (S-expressions). Grammatical rules, sentence structures, and syntactic trees are native AST structures that can be traversed, pattern-matched, and rewritten without serialization overhead.
• Compiled SBCL Performance: Steel Bank Common Lisp (SBCL) compiles directly to native assembly (x86-64), delivering performance competitive with optimized C++ while retaining dynamic functional expressiveness.
• Polyglot Microservice Boundary: The high-performance Lisp engine runs as a stateless, hermetic core service, wrapped in modern C++/Go/Java RPC interfaces for cloud scaling and observability.

✅ The Architectural Lesson:

Don't force a general-purpose language when a domain-specific paradigm (Lisp for symbolic AST manipulation) offers an order-of-magnitude reduction in latency and code complexity. Isolate specialized engines behind standard gRPC boundaries.

⚠️ The Production Gotcha:

Talent and tooling isolation. Operating uncommon runtime engines requires custom telemetry collectors, profiling tools, and specialized hiring, which is why boundary encapsulation is mandatory.

🎙️ The Staff Interview Soundbite:

"For complex rule-evaluation and symbolic AST processing, a Staff engineer evaluates execution paradigm over hype. As Grammarly demonstrated with Common Lisp, choosing a runtime with native tree homoiconicity compiled to machine code can yield 10x throughput advantages over standard enterprise runtimes, provided it is cleanly encapsulated behind standard network boundaries."

Layer 4 (Maglev) vs. Layer 7 (Envoy) Load Balancing

Nov 24 – Nov 29, 2026
First-Principles Architecture:

• Layer 4 (L4 / Maglev): Operates on TCP/UDP 5-tuple (Src IP, Src Port, Dst IP, Dst Port, Protocol). Does not inspect HTTP payload or terminate TLS. Uses ECMP (Equal-Cost Multi-Path) routing and consistent hashing lookup tables to achieve line-rate throughput without maintaining per-connection state on central routers.
• Layer 7 (L7 / Envoy): Terminates TLS, inspects HTTP/2 headers, paths, cookies, and gRPC methods. Employs an event-driven, non-blocking asynchronous thread model (libevent) with worker threads bound to hardware CPU cores.

✅ When to use L4 (Maglev):

Front-door packet routing where raw throughput is paramount (>1M QPS). Perfect for spraying incoming traffic across a pool of L7 proxies with zero connection drops during autoscaling.

⚠️ When L4 fails (Why you need L7):

L4 cannot do path-based routing (e.g. /api/checkout vs /api/search), cannot do gRPC stream-level load balancing, and cannot inspect JWT auth tokens or enforce per-tenant rate limits.

🎙️ The Staff Interview Soundbite:

"In a production system handling millions of requests per second, I would deploy a two-tiered ingress architecture: Maglev at Layer 4 using ECMP routing to distribute packets across a pool of Envoy Layer 7 proxies. Envoy terminates TLS and performs intelligent gRPC request-level load balancing, while Maglev ensures zero TCP connection reset storms during proxy rollouts."
